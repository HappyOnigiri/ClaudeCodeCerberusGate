# 開発と検証

## Git の運用

変更は作業ブランチでコミットし、必ず PR を作成して `main` に取り込む。

## Git hooks の導入

clone 後、リポジトリ内で次を実行する。

```sh
sh scripts/setup-hooks.sh
```

`main` 上のコミットは `pre-commit` hook が拒否する。
変更は作業ブランチでコミットし、PR 経由で取り込む。
hook は共通 Git ディレクトリに配置するため、同じリポジトリの worktree でも共有する。
既存の異なる `pre-commit` hook がある場合は上書きせず、エラーで停止する。

`core.hooksPath` は変更しない。
この設定がある環境では、指定先の hook が共通 Git ディレクトリの hook へ処理を引き継ぐ必要がある。

ローカル hook は `--no-verify` などで回避できるため、強制的な PR 制限には GitHub 側のブランチ保護も必要となる。

## 実地検証

実装後は必ず Claude Code を用いた実地検証を行う。利用量を節約するため、検証用に起動する Claude Code は `haiku` モデルを明示指定する。
この指定は検証用であり、プロダクトのレビュアーモデルの決定ではない。
静的検査やスタブテストだけで実装完了とせず、実際の利用経路で動作を確認し、結果を記録する。

Mods の検証では、実セッションで表示前の保留と公開を確認する。
中断、検証エラー、セッション再開、他の Mods との併用時にも、未検証本文が公開されず、検証済み本文と公開本文が一致するかを確認する。

## 検証環境の設計で検討する内容

以下は環境構築時の検討事項であり、コマンドや CI はまだ実装していない。

- フォーマット、Lint、型チェック、プラグインの検証・テストを共通の検査コマンドにまとめる。
- 通常の CI で使う Claude Code のバージョンを固定し、実際に使うエンジンが生成する型とテストキットを確認する。
- 純粋ロジックのテスト、イベント・API をスタブ化したテスト、実モデルとログインを使う実地検証を組み合わせる。
- 作業ツリーからローカル導入できる経路を用意し、同一バージョンの再導入、設定の保持、反映に必要な再起動を確認する。
- 最新版 Claude Code の互換性検査を通常の CI と分けるかを検討する。

実地検証のログや一時ファイルは `tmp/` に保存する。再利用する検証手順と運用ルールはこの文書へ反映する。
